Upsera Build Plan
Plan · v0.5 · built to compete with Uptime Kuma · awaiting review

Upsera: self-hosted uptime monitoring

A single Go service with an embedded web dashboard that checks HTTP endpoints, keywords, TCP ports and Docker containers, alerts you the moment something fails, and publishes shareable status pages. Ships as one docker compose up -d.

Positioning: Uptime Kuma is excellent for one person watching a homelab. Upsera targets the next step up: teams, multiple regions, fewer false alarms, and monitors managed as code.

Scope

What v1 delivers

Monitors

  • HTTP(S): method, headers, body, expected status codes, timeout, redirects
  • Keyword: page contains / does not contain text, optional case sensitivity
  • TCP port: connect check with latency
  • Docker container: running state plus healthcheck status
  • Ping, DNS record, and push (heartbeat URL for cron jobs) for parity
  • TLS certificate expiry warning on HTTPS monitors

Notifications

  • Telegram, Discord, Slack, Email (SMTP)
  • Generic webhook for anything else (ntfy, PagerDuty, n8n)
  • Down, recovered (with downtime), and cert-expiry events
  • Per-monitor channel selection, a "send test" button

Dashboard

  • All monitors with live state, latency and 24h / 30d uptime
  • Heartbeat bars, response-time chart, event log per monitor
  • Groups and tags, pause / resume, maintenance windows
  • Live updates without refresh (Server-Sent Events)
  • Brand dark pink #C2185B for primary actions, links and accents (text on pink is white); status colors stay semantic (green UP, red DOWN) and never use the brand pink. Dark theme by default

Status pages

  • Any number of public pages, each at /status/<slug>
  • Pick monitors, group them, rename them for the public
  • 90-day uptime bars and an overall status banner
  • Incident notes you post manually; optional custom domain
Differentiators

Where Upsera beats Uptime Kuma

Uptime Kuma has far more notification providers and monitor types. We will not win on breadth in v1, so we aim at the gaps its users have asked about for years: multi-location checks and multi-user support are both long-standing open requests on its GitHub.

Multi-location probes

A small upsera-probe binary you run on any VPS. It registers with a token, pulls its assigned monitors over HTTPS, and pushes results back. A monitor checked from Jakarta, Singapore and Frankfurt only goes DOWN if 2 of 3 fail, which removes most false alarms caused by one bad network path. Per-region latency is charted side by side.

Smart alerting

Escalation: notify Telegram now, email the team after 10 minutes if nobody acknowledged. Acknowledge with a button in Slack or Telegram. Dependencies: if the router is down, its 20 child services send one alert, not 21. Flapping monitors are held back until they settle.

Monitors as code

Every monitor, channel and status page can be described in YAML and applied with the CLI or from a CI job on every push, the same workflow as Terraform or Argo CD. The REST API underneath is the same one the dashboard uses, so nothing is UI-only.

SLOs and degraded state

Set a target like 99.9% over 30 days and see the remaining error budget. Burn-rate alerts warn you before the budget runs out. A service that answers in 4 s instead of its usual 200 ms is shown as DEGRADED instead of healthy.

Architecture

How the pieces fit

Each check result is written as a heartbeat. Only transitions (for example UP to DOWN) go on the event bus, so the dispatcher and the dashboard's live stream react to state changes rather than every check.

Remote probes report into the same pipeline. The server's built-in checker is itself a probe row named local, so every heartbeat has a probe_id. Each region applies its own retries and reports failure only after they are exhausted. For a multi-region monitor, the scheduler takes the latest result per selected region; a result older than 2× the monitor interval is stale and excluded. The monitor goes DOWN when failing regions ≥ quorum. If fewer fresh regions remain than the quorum, the monitor stays PENDING and a "probe silent" alert fires instead of DOWN.

Monitor definitions and channel configs are cached in memory at startup. If Postgres becomes unreachable, checks keep running and state changes still trigger alerts from the cached channels. Escalation timers, acknowledgements and dedupe keys are kept in memory and written to alerts and notification_log once the database is back. Heartbeats queue in a bounded buffer (HEARTBEAT_BUFFER_SIZE, default 100000); when it is full the oldest are dropped and the drop count is logged. A restart during an outage loses the in-memory state, so an ongoing outage may alert once more after the restart. The dashboard shows a "database unreachable" banner, and you get an alert about it too.

Alerting

Alert logic, the core feature

Fast, but not noisy. A single timeout should not wake you up; a real outage should reach you within one or two intervals.

UPcheck fails → PENDINGfails N retries → DOWNcheck passes → UP · latency above baseline →DEGRADED · paused / window active →MAINTENANCE

When it fires

  • DOWN after N consecutive failures (default 1 retry at a shorter retry interval), or when a quorum of regions fails
  • Recovered, including total downtime
  • DEGRADED when a region's p95 latency over a rolling 15-minute window stays above 3x that region's own 7-day baseline
  • SLO burn rate too high, TLS cert expiring in 14 / 7 / 1 days
  • Silenced during maintenance windows and when a parent dependency is already DOWN

How it delivers

  • Escalation policy per monitor: steps of channels with delays, stopped by an acknowledgement
  • Acknowledge from the dashboard or an inline button in Slack / Telegram. Slack buttons need the Slack app mode (bot token + app-level token, Socket Mode); plain incoming-webhook Slack channels get no buttons. Telegram buttons use long polling (getUpdates). Neither needs a public URL, so acks work behind NAT.
  • Flap damping: a monitor changing state too often sends one "flapping" alert
  • Each channel has its own queue; 3 attempts with backoff; every attempt logged
  • Dedupe key per monitor + event so restarts do not resend

Every provider implements one small Go interface, so adding Gotify, ntfy, WhatsApp or Teams later is one file each:

type Notifier interface {
    Type() string                              // "telegram", "discord", ...
    Validate(cfg json.RawMessage) error        // checked when the channel is saved
    Send(ctx context.Context, cfg json.RawMessage, ev Event) error
}

Channel secrets (bot tokens, SMTP passwords, webhook URLs) and Docker TLS keys are encrypted at rest with AES-256-GCM. The key is derived from APP_SECRET with HKDF-SHA256, and ciphertexts carry a v1: key-version prefix for rotation. Losing APP_SECRET makes them unrecoverable, so back it up with the database.

Outbound target policy (checks and webhook notifications): the resolved IP is checked at dial time to block DNS rebinding. Link-local and metadata addresses (169.254.0.0/16, fe80::/10) and the docker-proxy host are always refused. Private and loopback ranges are allowed by default for homelab use; an instance admin can block them. Checks never store or return response bodies; heartbeat messages are capped at 200 characters.

Delivery

Build phases

Each phase ends in something you can run. Teams, API tokens and a probe_id on every heartbeat go in from phase 1, because retrofitting them later means rewriting most queries. Phases 1 to 5 reach parity with Uptime Kuma plus team support and smarter alerting; phases 6 and 7 add multi-region checks, SLOs and monitors as code.

Foundation

  • Repo layout, config from env, Postgres via pgx + goose migrations, structured logging
  • Teams, users, roles, sessions, scoped API tokens, audit log
  • Scheduler with jittered start, worker cap, graceful shutdown
  • In-memory config cache and heartbeat write buffer so checks survive a database outage
  • Daily rollup into uptime_daily and retention pruning of raw heartbeats
  • Integration tests against a real Postgres container (testcontainers), run in CI from the first commit
  • HTTP, keyword, TCP, ping, DNS and push checkers plus TLS certificate expiry on HTTPS monitors, unit-tested against local test servers
  • REST API with OpenAPI spec generated from the handlers
done when: monitors are created via API and store heartbeats

Alerting engine

  • State machine (UP / PENDING / DOWN / MAINTENANCE, with DEGRADED reserved and detected in phase 7), event bus
  • Dispatcher with per-channel queues, retries, dedupe, log
  • Telegram, Discord, Slack, SMTP, generic webhook, plus test-send endpoint, cert-expiry events
  • Escalation policies, acknowledgement (web, Slack and Telegram buttons; Slack via Socket Mode, Telegram via long polling), dependency suppression, flap damping
done when: an unacknowledged outage escalates from Telegram to email, and a DOWN parent silences its children

Dashboard

  • Login, team switcher, monitor list with heartbeat bars, add / edit forms per monitor type
  • Monitor detail: latency chart, uptime 24h / 7d / 30d, event history, open alerts with Acknowledge
  • Channels, escalation policies, maintenance windows, members and tokens, SSE live updates
done when: everything above is manageable from the browser

Docker monitoring

  • Docker host config (socket proxy URL, or a remote host over TCP / TLS)
  • Container picker in the UI, checks for running state and health status
  • Messages like "exited (137)" or "unhealthy" surfaced in alerts
done when: docker stop on a watched container triggers an alert

Status pages

  • Page builder: sections, monitor selection, public names, branding, custom domain
  • Public page with overall banner, 90-day bars, incident timeline; responses cached 30s
  • Custom domains: a page is served when the request Host equals its custom_domain; the Caddy profile issues certificates with on-demand TLS, gated by GET /api/tls-allowed?domain= returning 200 only for published pages
  • Incidents auto-drafted when a listed monitor is DOWN for 5 minutes, published after you review
  • Subscribers by email (instance SMTP), webhook and RSS
done when: two public pages render with different monitors, and a subscriber gets the incident email

Multi-location probes

  • upsera-probe binary and upsera/upsera-probe image; register with a one-time token
  • Probes pull assignments and push results over HTTPS, with local buffering if the server is unreachable
  • Per-monitor region selection and quorum; per-region latency chart; alert when a probe goes silent
done when: firewalling the target from one probe's region fires no alert, from two regions fires DOWN, and stopping one probe fires "probe silent", not DOWN

SLOs and monitors as code

  • SLO targets, error budget view, multi-window burn-rate alerts, monthly SLA report
  • DEGRADED detection from rolling per-region p95 baseline
  • upsctl CLI: export, diff, apply for monitors, channels, policies and status pages; example GitLab CI job; export writes channel secrets as ${ENV_VAR} placeholders, never plaintext, and apply resolves them from the CLI's environment
done when: upsctl apply from CI creates the same setup on a fresh instance

Packaging and launch

  • Multi-stage Dockerfile (node build, go build, distroless runtime, non-root); time/tzdata embedded so TZ works; ping uses unprivileged ICMP sockets (no CAP_NET_RAW)
  • docker-compose.yml with local-db profile, .env.example for Supabase and local, healthcheck, backup notes
  • Optional Caddy profile for HTTPS, /metrics, docs site, README with a comparison table and screenshots
done when: fresh server to working dashboard in under 5 minutes

After v1

  • Kubernetes monitor: deployment ready replicas, crash-looping pods, via in-cluster service account
  • High availability: several app replicas sharing monitors through Postgres advisory locks
  • OIDC login (Google, GitHub), Terraform provider, more notifiers (ntfy, Gotify, Teams, PagerDuty native)
  • More monitor types: gRPC health, MQTT, database connection checks

Decisions for you

I will go with the recommendation on each unless you say otherwise.

1. Goal

Build a product that competes with Uptime Kuma.

decided: build

2. Backend language

Go matches your stack and lets the server, probe and CLI share one codebase.

decided: Go

3. Database

Postgres, either Supabase (managed, free up to 500 MB) or the bundled container. Same code, only DATABASE_URL changes.

4. Users

Teams and roles are now part of v1, since they are one of the main reasons to choose Upsera.

decided: teams with roles from phase 1

5. License

MIT (same as Uptime Kuma) is easiest to adopt. AGPL-3.0 stops someone from selling it as a hosted service without sharing changes. The repo already has an MIT LICENSE committed; switching to AGPL-3.0 must happen before accepting outside contributions.

recommended: AGPL-3.0 if you may offer a hosted version later, otherwise MIT

6. First public release

Release after phase 5 as v0.x to get users early, or wait for all 8 phases. A phase-5 release differentiates on teams and alert routing only; multi-region checks, SLOs and monitors as code land in phases 6–7.

recommended: public v0.x after phase 5, v1.0 after phase 8

7. Name and brand

Product name is Upsera. Server binary upsera, remote agent upsera-probe, CLI upsctl. Brand color is dark pink #C2185B (lighter #F06292 for text on the near-black #090C10 dark theme), deliberately distinct from Uptime Kuma's green #5CDD8B.
